## 方法

- 配置 multi=InspectionAgentRunner（Supervisor→planner→Send 扇出 inspector×N→reporter，默认拒绝审批）；single=SingleReActRunner（单 ReAct 循环）。同一 HybridRetriever（真实检索）、同一合规替身 LLM 工厂、同一 Budget 默认值。
- 合规替身按系统提示路由角色：multi 的 inspector 简报驱动（B6：遥测已在简报，不调 get_telemetry）；single 无简报逐台自取遥测——两配置信息面差异即真实设计差异，指标如实呈现。
- 指标复用 C8 run_case/aggregate（含 X1 双口径）：process-strict=期望集工具必须调用；goal-oriented=get_telemetry/list_devices 以结论覆盖判定、dispatch_drone 默认拒绝口径期望不调用。
- 真实模型口径未执行：总调用次数与 USD 为估算（调用数基线=离线替身每轮实测 LLM 调用数，真实模型的重试/循环行为可能高于此基线）。

## 结论（严格按计划 §11-E1 判定，不美化）

- 成功率差距 0.0pp < 3pp 判定线：离线合规替身口径下，单智能体成功率不差于多智能体（两配置均 100%）。
- 单智能体更优的维度：LLM 调用数（317 vs 375 次/轮）、步数（7.16 vs 9.78）、离线时延（P50 2.6 vs 7.6 ms，替身即时回复时编排开销主导，见已知偏差）。
- 多智能体更优的维度：输入 Token（146,548 vs 260,306/轮，子任务上下文隔离摊薄单轮上下文）；多设备并行的时延收益见 E3（真实 LLM 时延注入下的对照）。
- 按 §11 判定如实写明：本离线口径下若只看成功率与调用成本，单智能体已够用；多智能体的实证优势在上下文隔离（输入 Token）与并行扇出（E3），而非成功率。最终结论以真实模型重跑为准（费用估算见下节，等主线程确认预算）。

## 已知偏差

- 离线口径：成功率验证的是评测流程与契约管道，不代表模型效果。
- 时延不含真实 LLM 推理时间（替身即时回复）；两配置时延差只反映编排结构本身（并行 vs 串行的执行框架开销）。
- Token 为脚本估算（estimate_tokens：CJK 0.7 token/字，其余 4 字符 1 token），非计费口径。
- multi 的 reporter 对 warning/critical 一律起草工单（生产行为）：只诊断类 goal 下会与期望集错配，指标如实呈现。
- 真实模型估算假设 deepseek-chat 按 deepseek-flash 档计费（2026-10-25 定价页已不单列 deepseek-chat），跑前需确认。
